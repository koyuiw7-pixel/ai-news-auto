# 発表・検知から公開確認までの速度：定義と確認例

2026-10-31。速度の根拠を公開する前に、生成時刻、保存された出典日時、URLの公開確認時刻を分離した。比較対象の他媒体を測定していないため「どこよりも最速」という結論は出さない。

## 今回の修正

- `scripts/latency.py` は `sourcePublishedAt` の欠測を `publishedAt` で埋めない。後者には検知時刻による代用が含まれる。
- 日付のみ・精度不明の零時・タイムゾーンなし・日時不一致・負の時間・未確認を理由別に表示する。近くに検知しても、出典日時が精密である証明にはしない。
- 遅延が7日超でも捨てない。生成期間の中で古い発表を記事化した実績を残す。取りこぼし回収を新発表と同じ意味の速報として評価しない。
- `確認済み発表→公開確認` と `保存出典日時→公開確認（精度未監査を含む）` を別集計にした。後者は暫定の運用診断に使い、公式発表からの保証値として広告しない。
- 各指標は有効件数・除外理由を持つ。30分以内率は有効件数を分母にする。分母0は未算出。P90は昇順の `ceil(0.9 * n)` 番目（nearest-rank）へ固定した。以前のround型とは数値が変わり得る。
- グループ名を「Web出典の記事すべて（公式発表に限定しない）」へ修正。速報レーンにも二次報道を含む。グループ同士は重複するため足さない。
- `lib/articles.ts` の `speedLabel` は現行 `speedMinutes` だけでは表示しない。旧値は生成時点までの分数を切り上げ、固定3分を足した推定であり、公開確認の実測と一致するとは限らない。関数の呼出しと保存値は保持する。

生成処理・記事本文・SNSコード・既存予約・投稿履歴は変更していない。SNSで保存済みの速度表現まで今回訂正したとは扱わない。

## 公開確認時刻の意味

既存の `state/live_log.json.liveAt` は、デプロイ後の読み取りで当該記事URLのHTTP 200を初めて確認した時刻。厳密な初公開時刻ではなく、確認までの待ち時間も含む。本文・canonical・配信版の一致まではその時点で保存していない。したがってこの値を計算機の性能や純粋なデプロイ所要時間として表示しない。

現在の記録は生成から36時間以内・detectedAtありの記事を対象にし、成功を30日保持する。未記録は非公開の証拠ではない。記事化されなかった発表はこの母集団に入らない。レポート期間は生成日時による直近日数で、発表された全ニュースの捕捉率ではない。

## 公式日時を照合した3例

各公式ページの `meta name=published_time` と JSON-LD `datePublished` が、記事JSONの `sourcePublishedAt` と一致した。公式ページの `article:published_time` は日付のみだったため、そちらを分単位の根拠にはしていない。時刻はすべてUTC。

| 記事slug | 公式資料の発表日時 | URLの公開初確認日時 | 記録上の差 |
|---|---|---|---|
| `gemini-4-carbon-cybersecurity-model` | 2026-10-28 17:00:00 | 2026-10-28 17:05:17 | 5分17秒 |
| `gemini-notebook-free-textbooks` | 2026-10-29 16:00:00 | 2026-10-29 16:07:24 | 7分24秒 |
| `gemini-edit-files-directly` | 2026-10-29 16:15:00 | 2026-10-29 16:23:20 | 8分20秒 |

一次資料：

- [Gemini 4 Carbon](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-carbon/)
- [Gemini Notebookの教科書追加](https://blog.google/innovation-and-ai/products/gemini-notebook/new-access-textbooks/)
- [Geminiでのファイル編集](https://blog.google/innovation-and-ai/products/gemini-app/edit-files-directly/)

この3件は照合できた実例であり、代表性を保証する抽出ではない。3件の中央値や100%という率をサイト全体の速度と表示しない。現在の公式メタ情報との一致であり、歴史的な最初の発表を外部アーカイブで完全に証明したものではない。

`state/source_time_reviews.json` に公式URL・照合日時・確認した属性・保存日時・公式日時を残した。元記事のURLと日時が完全一致し、公式日時も一致する `verified / precision=timestamp` だけ確認済みとして扱う。記事のURL/日時が変われば古い確認を流用しない。今後記事を増やすだけで全件をverifiedにする仕組みではない。

## 日時不一致を保留した例

`claude-finds-critical-vulnerabilities` は、保存された出典日時が2026-10-30 01:57:31 UTC。一方、[公式ページ](https://www.anthropic.com/research/discovering-vulnerabilities-with-claude)はPublished Oct 27, 2026、`datePublished` も2026-10-27 00:00:00 UTCだった。本文には元記事が10月27日付であることが既に書かれている。

原因は当時の原日時・抽出フィールドを保存していないため未確定。時刻を推測で補正せず、レビュー記録を `conflict` とし、発表起点の速度集計から除外した。検知・生成・公開確認の各記録は残す。記事の元公開日・生成日は今回変更していない。日付表示と原発表日の整合は別途確認する。

## 運用判断と再導入条件

初回監査の固定スナップショットは2026-10-31 00:43:42 JST、記事765本のうち直近7日生成のweb記事257本。公開確認記録は183本、未記録74本。速報レーン27本のうち検知・公開確認を持つ26本は、検知から公開確認まで中央値6.5分、nearest-rank P90は14.4分、30分以内26/26だった。これは記録できた26本の過去実績で、全発表・全記事・将来の保証ではない。

保存された出典日時を使う暫定集計には、二次報道・古い発表・精度未監査を含む。生成が速いことと、発表直後に見つけたことは別々に改善する。通常レーンの生成後の待ち時間は確認の遅れを含むため、ジョブ待ち・デプロイ・初回確認の時刻がそろってから原因を決める。

時間バッジを再導入する場合は以下を満たす。

1. 原資料の日時、元の文字列、抽出フィールド、タイムゾーン、精度、推定の有無を保存し、発表と更新を区別する。
2. 対象記事のcanonical・本文または配信版の一致、公開確認時刻・確認元のrun/deploymentを記録する。失敗と未確認を保持する。
3. 出典日時不明・日付精度・日時矛盾では数字を出さない。実測と推定を同じラベルにしない。
4. 公開文言を「公開を確認するまで」など計測の意味に合わせ、期間・有効件数・欠測・サンプル選択を併記する。
5. 速度とGoogle登録・検索流入・比較遷移・承認収益を別段階で見る。速度だけでSEO/GEOの評価や粗利の増加を保証しない。
